## 명부 갱신 절차

원본 두 개는 해마다 새 판이 나오므로 사람이 판과 다운로드 기록을 확인하고 갱신한다.

1. 새 원본 두 개를 `scripts/raw/registry/` 에 둔다. 내려받은 날, 출처 페이지, 이용허락, 원본 기준을 기록한다. 원본을 data로 복사하거나 커밋하지 않는다.
2. 원본의 바이트 수와 SHA-256을 잰다. `git check-ignore scripts/raw/registry/*.csv`로 제외 여부를 확인하고 `git ls-files -- scripts/raw/registry`가 비어 있는지 확인한다.
3. 아래 명령에서 두 경로를 실제 원본으로 바꿔 실행한다. 멈추면 메시지의 칸과 값을 확인하고 원본 규격 변경 여부를 조사한다. 원인을 확인한 뒤 필요한 최소 수정만 하고 테스트한다. 멈춤을 우회하지 않는다.
4. 같은 원본으로 다시 실행해 두 산출의 SHA-256이 각각 같은지 확인한다. 출력 요약을 이전 값과 비교하고 위 원본 기록을 새 값으로 갱신한다. 단지명 불일치나 부동산원에 없는 단지가 0이 아니면 해당 단지들을 확인한다. 두 명부의 시점이 달라 단지코드가 다른 단지에 붙었을 수 있다. 이름까지 같으면 이 검사만으로 알아낼 수 없다.
5. 대응표 다시 만들기 -> 면적 매칭 다시 하기 -> 다시 적재 순서로 진행한다. 스냅샷 해시를 검사하는 스크립트가 있으면 기대값을 새 해시로 바꾼다.

```bash
python3 -m unittest scripts.test_registry
python3 scripts/registry.py --reb 'scripts/raw/registry/단지 원본.csv' --price 'scripts/raw/registry/공시가격 원본.csv'
shasum -a 256 data/reb-complex-seoul-apt.csv data/price-area-seoul-apt.csv
```

입력 검사 실패 시 기존 출력 두 개를 바꾸지 않는다. 출력 쓰기 중 디스크나 권한 오류는 이 보장 밖이다.
이 경우 같은 원본으로 다시 실행하고 두 해시를 확인한다.

### 생성 조건

| 항목             | 값                                                                 |
| ---------------- | ------------------------------------------------------------------ |

파일 자체에는 기준월 칸이 없다(컬럼 16개 고정). 이 표가 그 자리다.

### 위 절과 값이 다른 이유 - 자연키 병합 전/후

위 `강남구 커버리지` 절은 raw XML 행을 센 값이고, 이 절은 병합 후 DB 값이다. **둘은 다르며 그것이 정상이다.**

| 지표             | 병합 전 (정찰) | 병합 후 (DB)                    |
| ---------------- | -------------- | ------------------------------- |
| 거래 총건수      | 10,741         | **10,237** (`sum(trade_count)`) |
| DB 행 수         | -              | 10,196 (`count(*)`)             |
| 해제             | 702 (6.5%)     | **663 (6.48%)**                 |
| 직거래           | 369 (3.4%)     | **363 (3.55%)**                 |
| `aptSeq` 고유값  | 512            | **512**                         |
| 단지 기준 매칭률 | 39.3%          | **39.26%**                      |
| 건수 가중 매칭률 | 84.3%          | **84.16%**                      |

**약 500건 차이는 병합 설계상 정상이다.** 자연키가 같은 행이 합쳐지고, 해제 행은 거래로 세지 않고 정상 행에 도장만 찍는다.

비율은 분자/분모가 같이 줄어 차이가 0.15%p 이내다. **그래서 총건수를 대조 기준으로 쓰면 안 된다** - 정상 결과를 보고 버그를 찾게 된다.

`aptSeq` 고유값이 정찰 511 로 기록된 자리도 있다. **511 이 틀린 값이 아니라 다른 시점의 값이다** (정찰 2026-08-11~12, D3-5 2026-08-21). 총건수도 10,721 -> 10,741 로 함께 늘었다.

**[T] 서울 25구 표시 그룹 기준 무거래율은 25.21%이며, 무엇 중에서 셌는가 = 서울 25구에서 36개월간 등장한 (단지와 표시 그룹) 조합 15,975개 중 최근 12개월 거래가 1건 이상인 그룹 11,948개다.** 필터는 `is_current = true`, `deal_ym 202308~202607`이고 건수는 `sum(trade_count)`로 셌다.

- [T] 같은 실행의 원본 4자리 기준은 최근 거래 조합 15,083개 / 36개월 조합 20,907개 = 커버리지 72.14%, 무거래율 27.86%다. §10-1-4의 27.96%와 다른 이유는 그 문서 측정 뒤 신고가 유입됐기 때문이다. 표시 그룹 값 25.21%와 비교할 원본 기준은 27.96%가 아니라 같은 실행의 27.86%다.
- [T] `combos_1or2_valid`는 5,695 / 11,468 = 49.66%다. 판정과 화면, README에 쓰며 해제와 직거래를 제외한다. `combos_recent12m_group_valid` 11,468개가 이 판정용 값의 모수다.
- [T] `combos_1or2_all`은 5,853 / 11,948 = 48.99%다. 이전 산출물과 대조하는 용도 전용이며 화면과 README, ADR에 인용하지 않는다.
- [T] `_valid`의 정확한 정의는 "해제를 우선 적용하는 보수 판정을 거친 뒤 남은 거래가 1 또는 2건인 그룹"이다. 해제 여부가 불분명한 행은 정상 거래가 남아 있어도 행 전체가 빠지며, 이번 실행에서 영향받은 그룹은 4개다. [I] 분자와 모수가 함께 달라질 수 있으므로 편향 방향은 보장되지 않는다.
- [T] 이번 표시 그룹은 단지 면적 정보가 아니라 실거래에 등장한 면적만으로 만들었다. 단지 면적 정보를 축으로 삼는 M4 뒤에 값이 한 번 더 달라질 수 있다. [I] 묶음 개수는 반드시 줄거나 같지만 비율은 오르거나 내릴 수 있으므로 상한이라고 부르지 않는다. 실제로 관악구 커버리지는 원본 478/640 = 74.69%에서 표시 그룹 384/518 = 74.13%로 내려갔다.
- [T] 병합은 면적 오름차순에서 직전 원소와의 차가 1제곱미터 미만이면 이어 붙이는 체이닝 해석 A를 썼다. 그 결과 폭이 1제곱미터를 초과한 그룹은 서울 25구 합계 122개다.

## 강남구 자연키 감사

최근 3개월을 반복 수집하므로 재수집이 멱등해야 한다. 원본에 거래 ID 가 없어 컬럼 조합만으로 거래를 식별할 수 있는지 확인했다.

- 매매: 36개월 10,741행. 키 = aptSeq + 계약년/월/일 + 전용면적 + 층 + 거래금액
- 전월세: 2026-07 단월 1,130행. 키 = 위 조합에서 거래금액 대신 보증금 + 월세

```
python3 scripts/recon.py --audit-key          # 매매
python3 scripts/recon.py --audit-key --rent   # 전월세
```

'페이지 분할' 과 '응답 정렬 편향' 두 절을 뺀 나머지는 위 명령으로 재현된다.
그 둘은 일회성 분석이며 스크립트를 남기지 않았다.

### 유일성

| 지표                      | 매매   | 전월세 |
| ------------------------- | ------ | ------ |
| 키를 못 만든 행           | 0      | 0      |
| 총 행 수                  | 10,741 | 1,130  |
| 고유 키                   | 10,183 | 1,094  |
| unique 인덱스가 지우는 행 | 41     | 36     |

지워지는 행을 자연키 밖의 칸까지 비교해 성격을 나눴다 (매매는 해제 행 제외).

| 성격               | 매매 키/지워지는 행 | 전월세 키/지워지는 행 | 정보 손실               |
| ------------------ | ------------------- | --------------------- | ----------------------- |
| 전 칸이 동일       | 16 / 16             | 21 / 23               | 없음                    |

- 전월세 충돌 1건은 `역삼래미안 / 80.87㎡ / 19층 / 보증금 130,000` 의 preDeposit 이 117,300 과 110,300

- cdealType 이 'O' 도 빈 값도 아닌 행 0건. 해제 판정을 이진으로 다뤄도 된다

### 금액을 뺀 키 - 정정 이력 추적은 불가

자연키 후보가 아니다. 금액만 바뀐 같은 거래를 같은 identity 로 이을 수 있는지 보려고 따로 측정했다. 이 키로 묶였으나 금액이 실제로 다른 그룹이 21개(정상만 14 / 해제 섞임 7).

**21건 안에 정정이 아닌 것이 섞여 있고 원본으로 구분할 수 없다.**

- `11680-4003` 은 110,000 해제 후 109,000 재신고. 정정 패턴
- `11680-4929 / 2024-06-23 / 59.92㎡ / 16층` 은 198,000(동 120)과 214,500(동 102). 동이 다른 별개 거래
- aptDong 채움률이 78.9% 라 동을 넣어 가려낼 수도 없다

금액 변경 이력을 별도 테이블로 두더라도, 어느 행이 어느 행의 정정인지 잇는 기준으로는 이 키를 쓸 수 없다.

## 적재 규칙

'빈 값 vs 채워진 값' 이 매매 19키, 전월세 11키로 중복의 최대 유형이다. 원인은 서로 다르다.

- **전월세**: 거래신고 자료와 확정일자 자료를 합친 API 다. 해당 11키의 두 행이 전부 '앞 블록 1행 + 본문 1행' 조합이다(idx 0 과 512, 1 과 82, 3 과 808). 앞 블록은 계약구분/계약기간/종전보증금이 없는 확정일자 계열이다. **시간이 지나 채워지는 것이 아니라, 재수집해도 같은 응답에 계속 두 행이 온다**
- **매매**: 위치가 불규칙하다(idx 47/879, 153/295). 등기 완료 시점 차이로 보이나 확정하지 못했다

1. **빈 값이 채워진 값을 덮어쓰지 않는다.** `DO UPDATE SET x = EXCLUDED.x` 를 그대로 쓰면 이미 확보한 등기일, 동, 계약구분이 지워진다. `COALESCE(NULLIF(EXCLUDED.x, ''), 기존값)` 형태가 필요하다
2. **배치 안에서 자연키별로 먼저 병합한 뒤 한 번에 적재한다.** 전월세는 두 행이 같은 응답에 들어 있어, 행 단위로 순차 upsert 하면 처리 순서에 결과가 의존한다. 순서가 바뀌면 결과가 바뀌므로 멱등하지 않다. 1번 규칙만으로는 막지 못한다
3. **결측 처리 규칙을 감사와 똑같이 맞춘다.** 감사(`recon.py` 의 `_BLANK_DEFAULT`)는 monthlyRent 가 빈 값일 때만 `0` 으로 채우고, 나머지 키 칸은 빈 값이면 행을 버린다. 적재가 더 느슨하면 DB 행 수가 감사보다 많아지고, 더 엄격하면 적어져 유일성 결론을 그대로 쓸 수 없다. deposit 은 결측과 0 이 다른 사실이므로 기본값을 두지 않는다
