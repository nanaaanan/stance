## 강남구 자연키 감사

최근 3개월을 반복 수집하므로 재수집이 멱등해야 한다. 원본에 거래 ID 가 없어 컬럼 조합만으로 거래를 식별할 수 있는지 확인했다.

- 매매: 36개월 10,741행. 키 = aptSeq + 계약년/월/일 + 전용면적 + 층 + 거래금액
- 전월세: 2026-07 단월 1,130행. 키 = 위 조합에서 거래금액 대신 보증금 + 월세

```
python3 scripts/recon.py --audit-key          # 매매
python3 scripts/recon.py --audit-key --rent   # 전월세
```

'페이지 분할' 과 '응답 정렬 편향' 두 절을 뺀 나머지는 위 명령으로 재현된다.
그 둘은 일회성 분석이며 스크립트를 남기지 않았다.

### 유일성

지워지는 행을 자연키 밖의 칸까지 비교해 성격을 나눴다 (매매는 해제 행 제외).

| 성격               | 매매 키/지워지는 행 | 전월세 키/지워지는 행 | 정보 손실               |
| ------------------ | ------------------- | --------------------- | ----------------------- |
| 전 칸이 동일       | 16 / 16             | 21 / 23               | 없음                    |

**실제 손실 후보는 매매 6건(0.056%), 전월세 1건(0.088%).** 동/호 정보가 없는 전월세 자연키가 더 약할 것이라는 예상은 실측으로 부정됐다.

- 매매 충돌 6키가 갈리는 칸은 estateAgentSggNm 3, rgstDate 3, aptDong 2
- aptDong 이 갈리는 2키는 별개 거래로 확정. `럭키(963) / 2024-07-06 / 84.97㎡ / 6층 / 195,000` 에 101동과 102동
- 전월세 충돌 1건은 `역삼래미안 / 80.87㎡ / 19층 / 보증금 130,000` 의 preDeposit 이 117,300 과 110,300
- 매매 거래 건수 분포 {1건: 10,142키, 2건: 41키}. 같은 자연키에 3건 이상은 36개월간 없음
- 매매 해제 702건 중 179건은 정상 행 없이 해제 통지만 존재
- cdealType 이 'O' 도 빈 값도 아닌 행 0건. 해제 판정을 이진으로 다뤄도 된다

### 금액을 뺀 키 - 정정 이력 추적은 불가

자연키 후보가 아니다. 금액만 바뀐 같은 거래를 같은 identity 로 이을 수 있는지 보려고 따로 측정했다. 이 키로 묶였으나 금액이 실제로 다른 그룹이 21개(정상만 14 / 해제 섞임 7).

**21건 안에 정정이 아닌 것이 섞여 있고 원본으로 구분할 수 없다.**

- `11680-4003` 은 110,000 해제 후 109,000 재신고. 정정 패턴
- `11680-4929 / 2024-06-23 / 59.92㎡ / 16층` 은 198,000(동 120)과 214,500(동 102). 동이 다른 별개 거래
- aptDong 채움률이 78.9% 라 동을 넣어 가려낼 수도 없다

금액 변경 이력을 별도 테이블로 두더라도, 어느 행이 어느 행의 정정인지 잇는 기준으로는 이 키를 쓸 수 없다.

### 페이지 분할 (일회성 분석)

같은 구간을 페이지 수만 다르게 두 번 받아 대조했다. 매매와 전월세는 엔드포인트가 다르므로 각각 확인했다.

| 대상           | 수집 방식                    | 결과                                                |
| -------------- | ---------------------------- | --------------------------------------------------- |
| 전월세 2026-07 | 1콜(2,000) vs 2콜(1,000+130) | 행/고유키/중복키 전부 일치                          |
| 매매 2025-03   | 1콜(1,000) vs 10콜(100씩)    | 전 칸 멀티셋 일치. 누락 0, 중복 0, 행 순서까지 동일 |

**페이지를 나눠 받아도 행 집합이 바뀌지 않는다.** 강남구는 월 최대 917건이라 기본 설정으로는 늘 1페이지지만, 25개 구로 확장하면 1,000건을 넘는 구간이 생긴다. 검정 대상은 신고가 끝난 과거 달이며, 유입 중인 최근 3개월은 미해결 참조.

### 응답 정렬 편향 - 전월세만 해당 (일회성 분석)

전월세 1,130행을 응답 순서 그대로 앞에서부터 잘라 봤다.

| 구간       | contractType 공백 | preDeposit 채워짐 |
| ---------- | ----------------- | ----------------- |
| 앞 10건    | **100.0%**        | 0.0%              |
| 앞 100건   | 24.0%             | 29.0%             |
| 전체 1,130 | **2.1%**          | 48.1%             |

**공백 24행이 인덱스 0~23 에 예외 없이 연속으로 몰려 있다.** 첫 페이지만 보면 "명세에 있는 필드가 100% 비어 있다"는 잘못된 결론이 나온다. 표본을 볼 때는 numOfRows 를 크게 잡고 전량 분포를 본다.

매매(2025-03, 917행)에는 이 구조가 없다. rgstDate 빈 행 82건, aptDong 빈 행 136건, 해제 75건이 100행 구간마다 고르게 흩어져 있다.

### 필드 실제 형식 - 매매 (10,741행)

| 필드             | 태그없음 | 빈값   | 채워짐 | 비고                               |
| ---------------- | -------- | ------ | ------ | ---------------------------------- |
| cdealType        | 0        | 10,039 | 702    | 값은 'O' 뿐                        |
| cdealDay         | 0        | 10,039 | 702    | cdealType 과 채움 수가 정확히 일치 |

| dealingGbn       | 0        | 0      | 10,741 |                                    |
| aptDong          | 0        | 2,269  | 8,472  | 78.9%                              |
| umdCd            | 0        | 0      | 10,741 | 매매에만 있음                      |
| landLeaseholdGbn | 0        | 0      | 10,741 |                                    |

- floor 1 ~ 68, dealAmount 결측/형식 오류 0건
- excluUseAr 소수 자리수 {1: 956, 2: 7,497, 3: 1,145, 4: 1,007}. **5자리 이상 없음 -> numeric(9,4) 로 원본 보존 가능**

- **aptDong 이 채워진 행은 rgstDate 도 100% 채워져 있다** (동반 8,472 = 동 8,472). 역은 성립하지 않음(등기만 있고 동이 없는 행 818건)

| 필드           | 빈값 | 채워짐 | 비고                                       |
| -------------- | ---- | ------ | ------------------------------------------ |
| contractType   | 24   | 1,106  | 신규 / 갱신                                |
| contractTerm   | 24   | 1,106  | `26.07~28.07`                              |

| useRRRight     | 852  | 278    | 값은 '사용'                                |

## 적재 규칙

'빈 값 vs 채워진 값' 이 매매 19키, 전월세 11키로 중복의 최대 유형이다. 원인은 서로 다르다.

- **전월세**: 거래신고 자료와 확정일자 자료를 합친 API 다. 해당 11키의 두 행이 전부 '앞 블록 1행 + 본문 1행' 조합이다(idx 0 과 512, 1 과 82, 3 과 808). 앞 블록은 계약구분/계약기간/종전보증금이 없는 확정일자 계열이다. **시간이 지나 채워지는 것이 아니라, 재수집해도 같은 응답에 계속 두 행이 온다**
- **매매**: 위치가 불규칙하다(idx 47/879, 153/295). 등기 완료 시점 차이로 보이나 확정하지 못했다

1. **빈 값이 채워진 값을 덮어쓰지 않는다.** `DO UPDATE SET x = EXCLUDED.x` 를 그대로 쓰면 이미 확보한 등기일, 동, 계약구분이 지워진다. `COALESCE(NULLIF(EXCLUDED.x, ''), 기존값)` 형태가 필요하다
2. **배치 안에서 자연키별로 먼저 병합한 뒤 한 번에 적재한다.** 전월세는 두 행이 같은 응답에 들어 있어, 행 단위로 순차 upsert 하면 처리 순서에 결과가 의존한다. 순서가 바뀌면 결과가 바뀌므로 멱등하지 않다. 1번 규칙만으로는 막지 못한다
3. **결측 처리 규칙을 감사와 똑같이 맞춘다.** 감사(`recon.py` 의 `_BLANK_DEFAULT`)는 monthlyRent 가 빈 값일 때만 `0` 으로 채우고, 나머지 키 칸은 빈 값이면 행을 버린다. 적재가 더 느슨하면 DB 행 수가 감사보다 많아지고, 더 엄격하면 적어져 유일성 결론을 그대로 쓸 수 없다. deposit 은 결측과 0 이 다른 사실이므로 기본값을 두지 않는다
