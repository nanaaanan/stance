# 003. 수집 배치 실행 방식으로 GitHub Actions를 선택한 이유

- 상태: 확정
  - 시점 : 코드 작성 전/선택 전 (`.github/workflows/collect.yml` 작성 전)
  - 질문 : 수집 배치를 어떤 방식으로 예약, 실행할 것인가
  - 핵심 : 트레이드오프 (실행 시간 한도 vs 상시 인프라 비용)

## 맥락

국토교통부 실거래 API 는 1콜이 (구, 계약월) 하나다. 서울 25구를 받으려면 콜 수가 이렇게 된다.

| 작업               | 규모                    | 실측 콜 수         |
| ------------------ | ----------------------- | ------------------ |
| 초기 적재 - 매매   | 25구 x 36개월           | **901**            |
| 초기 적재 - 전월세 | 25구 x 25개월           | **833**            |
| 초기 적재 합계     |                         | **1,734**          |
| 매일 재수집        | 25구 x 최근 3개월 x 2종 | **164** (명목 150) |

명목보다 많은 이유는 한 (구, 계약월) 이 여러 페이지일 수 있어서다. 전월세가 특히 그렇다 - 강남구 2026-07 이 2페이지다.

**요청 간 0.2초 스로틀이 API 규격상 필수다.** 명세가 30tps 이고 여유를 둬 초당 5건으로 잡았다. 초기 적재는 스로틀 대기만 약 6분이고, 실제 소요는 응답 시간과 Supabase 적재가 지배한다. **매일 재수집 164콜의 실측이 12분 56초다.**

여기에 두 가지 성질이 더 있다.

- **수집 파이프라인은 파이썬이다.** 표준 라이브러리만 쓴다. 앱은 Next.js + TypeScript 다
- **이 배치는 하루 1회 13분 돈다.** 나머지 23시간 47분은 아무것도 하지 않는다

## 검토한 선택지

배치를 어떤 방식으로 예약, 실행할 것인가. 판단 축은 셋이다 - **실행 시간 한도**, **언어**, **늘어나는 운영 표면**.

| 실행 방식                     | 선택지                                                                   | 판단 근거                                                                                                                                                                                                                                                |
| ----------------------------- | ------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 요청 기반 함수                | **Vercel Cron + Route Handler**                                          | 함수 실행 시간 제한이 있다. 초기 적재 1,734콜은 물론이고 매일 164콜(12분 56초)도 한도를 넘는다                                                                                                                                                           |
| 요청 기반 함수                | **Supabase Edge Function**                                               | 같은 실행 시간 제약. 더해서 Deno 런타임이라 파이썬 파이프라인과 언어가 갈린다. 파서와 정규화 규칙이 두개가 된다                                                                                                                                          |
| 요청 기반 함수                | **AWS Lambda + EventBridge Scheduler**                                   | 함수 타임아웃이 900초(15분)로 고정이고 늘릴 수 없다. 매일 12분 56초가 이미 그 턱밑이라 구가 늘거나 응답이 느려지면 그날로 깨진다. 초기 적재는 애초에 불가                                                                                                |
| 관리형 컨테이너 배치          | **Cloud Run Jobs + Cloud Scheduler** (AWS Fargate 예약 작업도 같은 부류) | 실행 시간이 문제가 아니다. 기본 10분, 최대 168시간이라 여유가 크고 컨테이너라 파이썬도 그대로 쓴다. 가장 강한 대안이었다. 기각 사유는 운영 표면이다. 이미지 빌드, 레지스트리, IAM, 결제 계정이 새로 생기고 수집 코드와 스케줄 위치가 각각 다른 곳이 된다 |
| 상시 실행 워커                | **VPS 기반 워커, 상시 실행 Fly.io 앱**                                  | 실행 시간 제약이 없다. 그러나 하루 13분 도는 일에 24시간 인프라다. 비용과 운영 부담(패치, 모니터링, 재기동)이 얻는 것보다 크다                                                                                                                           |
| **저장소 기반 예약 자동화**   | **GitHub Actions 예약 워크플로**                                        | job 당 6시간 한도라 여유가 크다. 공개 저장소는 무료. 시크릿 관리가 내장이다. 저장소와 같은 곳에 있어 수집 코드와 스케줄이 한 커밋에 함께 버전 관리된다                                                                                                   |

> 요청 기반 함수 -> 손님 올때만 문여는 가게다. 빨리 끝나는 일을 전제로 만들어졌고 클라우드 회사가 짧은 시간 제한을 건다. 해당 수집 범위를 늘리거나 API가 느려지는날 바로 수집이 깨질만큼 아슬아슬한 시간 제한이다. 더불어 해당 수집은 API가 막히지 않으려면 매번 0.2초씩 쉬어야 한다. 원본 데이터 API 구조상 빨리 수집을 끝내기 어려워 탈락했다.

> 관리형 컨테이너 배치 -> {내프로그램,언어버전,라이브러리,OS설정}을 통째로 한 컨테이너 상자에 넣고, 그 상자를 정해진 시각에 열어서 한번 돌리고 닫는것이다. 시간 제한 충분하다. 강한 선택지이나, GitHub Actions 예약 워크플로보다 우위가 아니다. <u>하루 13분짜리 일에 새로 만들 세팅이 늘어나고, 코드와 스케줄이 서로 다른 곳에 있게 되는 것이 큰 탈락 사유다.</u> 코드는 github에, 스케줄은 GCP콘솔에 이렇게 갈라진 경우 둘이 어긋나도 모를 수 있는 위험이 있다. '왜 하루에 두번 돌지?'싶으면 GCP콘솔을 열어봐야 하고, 이 변화를 만든 정확한 기록을 git에서 찾기 어렵다. (컨테이너 선택 조건: 배치가 3시간 넘게 걸려 Actions의 6시간이 빠듯한 경우, 정해진 시각에 정확히 돌아야하는 경우, 메모리 16GB등이 필요한 경우, 배치가 여러개고 순서가 있는 경우, 이미 GCP/AWS를 쓰고 있는 경우)

> 상시 실행 워커 -> 24시간 켜둔 내 작업실이다. 시간 제한 없다. 근데 하루 13분 쓰자고 24시간 서버를 켜두는 셈이다. 안써도 돈이 들고, 보안 패치하고 죽으면 살려야한다. 또한 배포 대상과 결제 계정과 시크릿 보관처가 각각 하나씩 늘어난다.

## 결정

**GitHub Actions 로 돌린다.**

> 필요할 때만 잠깐 컴퓨터를 빌려주는데(서버리스처럼), 6시간까지 길게 쓸 수 있다(워커/컨테이너처럼). 그리고 코드가 이미 Github에 있으니 만들게 yaml 파일이 전부다. 파서를 고치면서 주기도 바꿔야 하면 한 번에 끝난다. "1월 1일에 어떤 코드가 어떤 스케줄로 돌았나"와 같은 내용이 git log에 통째로 남는다. (컨테이너 쓰려면 하루 13분 도는 작업에 초기설정 작업이 많고, 코드 위치와 스케줄 위치가 갈라지므로 어긋나면 파악이 어렵다.)

세 가지가 맞물린다.

1. **요청 기반 함수는 실행 시간이 병목인데, Actions는 여유가 있다.** 요청 기반 함수에 맞춰 배치를 쪼개면 "어디까지 받았는가"를 관리하는 상태가 하나 늘어난다
2. **언어를 안 바꿔도 된다.** 로컬에서 원래 돌리던 파이썬 스크립트를 그대로 부른다. 수집 로직이 한 벌로 남는다
3. **코드와 스케줄이 같이 움직인다.** 파서를 고치면서 주기를 바꿔야 할 때 한 PR 로 끝나고, 어느 코드가 어느 스케줄로 돌았는지가 커밋 히스토리에 남는다

**초기 적재는 Actions로 돌리지 않았다.** 로컬에서 파이썬으로 한 번 돌렸었고, 워크플로는 매일 164콜만 맡는다. 그래서 Actions에 30분 타임아웃을 걸어 뒀다. 6시간 한도를 다 쓸 일이 없고, 무한 루프가 6시간을 태우게 두지 않는다.

## 포기한 것 — 무엇을 만들지 않기로 했고 왜

### 1) 수집 코드까지 TypeScript 로 통일하는 것

앱이 TypeScript 인데 수집만 파이썬이다. **레포 전체가 한 언어면 단순하다.** 타입을 앱과 공유하고, 테스트 도구를 하나로 쓰고, 새로 읽는 사람이 한 언어만 알면 된다.

**그런데 실행 방식 적합성을 언어 통일보다 위에 뒀다.** 이 배치가 필요로 하는 것은 긴 실행 시간, 스로틀을 지키는 순차 호출, 표준 라이브러리만으로 도는 가벼움이다. 파이썬 스크립트를 GitHub Actions 예약 워크플로로 돌리는 조합이 거기에 가장 잘 맞는다. 이 워크플로의 job은 GitHub-hosted runner에서 실행된다. **언어를 맞추려고 실행 방식을 요청 기반 함수로 옮기면 앞의 표에서 탈락한 제약을 그대로 떠안는다.**

**대가는 레포에 언어가 둘이 됐다는 것이다.** 앞으로 면적 반올림 같은 규칙이 앱과 수집 양쪽에 필요해지면 두 언어로 두 번 구현하게 되고, 두 구현이 어긋나면 화면 숫자와 DB 숫자가 다르게 나온다. **이 위험을 없앤 것이 아니라 안고 간다.**

### 2) 실행 시각을 내가 통제하는 것

GitHub Actions 의 스케줄은 지정한 시각을 보장하지 않는다. **공식 문서가 명시한다** - _"`schedule` 이벤트는 GitHub Actions 워크플로 실행 부하가 높은 시간대에 지연될 수 있다."_ 매시 정각이 그 시간대이고, 대기 중인 job 이 드롭되는 경우도 있다고 적혀 있다. 상시 실행 워커였다면 초 단위로 통제됐다.

**정시 실행이 필요한 설계였다면 이 선택은 틀렸을 것이다.** 장 마감 시각에 맞춰 계산해야 한다거나 다른 배치와 순서를 맞춰야 한다면, 지연과 드롭이 그대로 결함이 된다.

**이 서비스에 필요한 것은 하루 1회 신선도뿐이라 감수한다.** 받는 것은 계약월 단위 데이터라 05:17 에 돌든 06:00 에 돌든 같은 응답이 온다. 그래서 정각을 피해 17분으로 잡아 지연 확률만 낮춰 뒀다.

**대가는 "언제 갱신됐는가"를 약속할 수 없다는 것이다.** 화면에 "매일 새벽 5시 갱신"이라고 쓰면 거짓이 될 수 있다. 그래서 그렇게 쓰지 않고 마지막 갱신 시각을 표시하는 쪽으로 간다.

### 3) 60일 무커밋 시 스케줄이 꺼지는 것을 인프라 차원에서 막는 것

공개 저장소는 60일간 활동이 없으면 스케줄 워크플로가 자동 비활성화된다. 상시 실행 워커에는 이런 규칙이 없다. **Actions 를 고른 대가로 이 규칙을 떠안았다.**

`data/last-run.txt` 를 주기적으로 갱신하는 keepalive job 을 뒀다. **그러나 이것은 해결이 아니라 회피다. 두 가지 의미에서 그렇다.**

**첫째, 효과를 검증할 방법이 없다.** GitHub 은 "repository activity" 가 무엇인지 정의한 적이 없다. 커밋인지, 봇 커밋도 인정되는지, 기본 브랜치여야 하는지 나와있지 않다. 그래서 이 방어가 실제로 동작하는지는 60일이 지나야만 알 수 있고, 그때는 이미 늦다. 가장 개연성 높은 형태(주기적 push)를 골랐을 뿐 보장은 없다. (대안: 7일 후 동작 여부 확인 예정)

**둘째, 방어 대상이 방어 수단을 죽인다.** keepalive 는 워크플로 안에 있다. 워크플로가 비활성화되면 keepalive 도 함께 멈춘다. **살아 있을 때만 동작하는 방어이고, 죽은 뒤에는 자기를 되살리지 못한다.**

**그래서 실제 backstop 은 keepalive 가 아니다.** GitHub 이 비활성화 5일 전에 보내는 경고 메일과, 그 메일을 받고 사람이 누르는 재활성화 버튼이다. keepalive 는 그 메일을 받을 확률을 낮추는 장치이지 없애는 장치가 아니다.
