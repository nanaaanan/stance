# 001. 로그인 인증을 게이트가 아니라 승격 경로로 설계한 이유

- 상태: 확정
- 날짜: 2026-08-11

## 맥락

이 앱은 개인화된 데이터(임장 기록, 저장한 단지) 보관이 필수이므로, "지금 이 방문자가 누구인지"를 식별하는 수단이 필요하다.

이 앱의 첫 관문은 온보딩 8문항이다. 그런데 로그인 인증까지 더해지면 관문이 두 개가 되고, 사용자는 서비스의 핵심 가치를 경험하기도 전에 인지적 마찰을 겪고 이탈할 확률이 높다고 생각했다.

성공적인 온보딩의 본질은 사용자를 리텐션의 핵심인 '아하 모먼트'로 직행하게 만드는데 있다. 따라서 첫 방문자의 진입장벽을 낮추기 위해 로그인 시점을 가치경험 이후로 지연시키고, 아하 모먼트까지의 여정을 최단 경로로 압축하는 UX구조를 기획했다.

궁극적으로 이러한 사용자 경험을 실제 시스템 상에서 어떻게 구현할 수 있을지에 대한 기술적 타당성과 해결방안을 검토 및 결정하고자 했다.

## 검토한 선택지

1. 구글 OAuth 게이트 : 원래 계획. 마이페이지 진입 시 로그인 요구

- 저장, 기록 기능을 보려면 개인 구글 계정을 연결해야 한다. 처음 방문한 사람은 너무 많은 개인정보 요구에 그 버튼에서 이탈할 가능성이 있다.

2. 인증 없음(localStorage 저장) : 마찰이 0이다

- 그러나 기기를 바꾸면 기록이 사라지고, RLS로 서버에서 접근을 통제할 수 없다

3. 공유 데모 계정 : 구현이 복잡하지 않다

- 하나의 계정을 모두가 쓴다. 방문자 A가 쓴 임장 기록을 방문자 B가 본다. 데이터 오염이 구조적으로 발생한다.

4. 익명 세션 기본 + 구글은 승격 :

- 진입 즉시 로그인 정보가 없다면 signInAnonymously()로 익명 세션을 발급하고, 필요해지는 시점에 linkIdentity('google')로 승격을 제안한다

## 결정

4번을 채택

- 방문자는 개인정보(로그인, 회원가입 개인정보)입력 없이도 저장, 기록 기능을 쓸 수 있다
- 승격 시 user id 가 유지되므로 그때까지 쌓인 데이터가 그대로 따라온다
- "체험 계정으로 둘러보기" 도 익명세션으로 구현하면 방문자마다 세션이 분리되어, 3번의 데이터 오염 문제가 구조적으로 사라진다.

## 승격 트리거는 하나가 아니다

> 그중 하나는 이 앱의 핵심 동선이다.

| 트리거                               | 이 앱에서의 성격                                                                                                                                              |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| PC &rarr; 모바일 전환                | [핵심동선] **희소한 사건이 아니라 O2O 루프의 필수 구간.** 손품(PC)에서 단지를 고르고 저장 &rarr; 임장(모바일)에서 현장 기록. 앱을 제대로 쓰면 반드시 마주친다 |
| 기록이 쌓여 손실이 아까워질 때       | 임장 기록 3건 시점. 승격 유도 문구를 띄우기 가장 좋은 지점                                                                                                    |
| 배우자, 가족과 공유                  | 부동산 결정은 대개 2인 이상이 관여한다                                                                                                                        |
| 브라우저 데이터 삭제, 시크릿 창 종료 | 손실을 실제로 겪은 뒤                                                                                                                                         |

## "로그인을 강제하지 않으면 서비스가 손해 아닌가"

- 일반 프롭테크 앱이 로그인을 강제하는 이유는 잠재고객, 즉 리드 수집이다(중개업체 연결, 광고 타게팅, 재방문 유도) 이 앱은 그 비즈니스 모델이 아니다.

- 목표는 사용자 획득이 아니라 사용자의 의사결정 품질 향상이다. 따라서 로그인 계정은 목적이 아니라 수단이다.

## 구현하며 확인한 것

Supabase 의 익명 사용자는 anon 이 아니라 `authenticated 역할`을 받는다는 것이다.(JWT 에 role=authenticated, is_anonymous=true) 즉 "익명"은 로그인하지 않은 상태가 아니라 "이름 없는 로그인 사용자"였다.

이걸 모른 채 RLS 정책만 만들었다가 permission denied for table (42501, HTTP 403) 을 만났다.
RLS 는 "어느 행을 볼 수 있는가"를 정하는 층이고, 그 앞에 "이 테이블을 건드릴 수 있는가"를
정하는 GRANT 층이 따로 있었다. 두 층을 구분하고 나서 테이블 성격별로 권한 원칙을 나눴다.

| 성격                                 | GRANT                                       | RLS                  |
| ------------------------------------ | ------------------------------------------- | -------------------- |
| 공개 데이터 (실거래, 단지 마스터)    | anon, authenticated — SELECT만              | using (true)         |
| 사용자 데이터 (저장 단지, 임장 기록) | authenticated — SELECT/INSERT/UPDATE/DELETE | auth.uid() = user_id |

## 감수한 트레이드오프

- MAU 증가 : Supabase 는 월간 활성 사용자 수로 과금하고 익명 사용자도 1명으로 센다.구글 게이트라면 로그인한 사람만 세지만, 익명 우선은 방문자 전원이 MAU 가 된다. 무료 한도 5만에 도달하려면 이 앱 트래픽에서는 남용 외에 방법이 없다.(승격해도 user id 가 유지되므로 여전히 1 MAU 다 — 승격은 비용을 늘리지 않는다)
- 자동 정리 없음 : auth.users 에 계속 누적된다. 개발 중 본인 테스트도 카운트되며 브라우저, 기기, 시크릿 창마다 새 사용자가 생긴다.
- CAPTCHA 미적용 시 남용 : 공개 URL 이므로 유일하게 실재하는 리스크다 &rarr; Cloudflare Turnstile 연동 예정

위 3가지는 병렬적인 현상이 아니라 인과관계다.

> CAPTCHA 없음 &rarr; 남용(익명 세션 무제한 생성) &rarr; 행 폭증 &rarr; MAU 초과 / DB 비대

해결방법 : CAPTCHA쪽 한군데만 막으면 나머지는 발생하지 않는다.

## 포기한 것 — 무엇을 만들지 않기로 했고 왜

- 로그인 화면을 만들지 않는다 : 로그인은 화면이 아니라 마이페이지 안의 한 줄 ("기기를 바꿔도 기록을 유지하려면")로 존재한다. 별도 라우트를 만들면 그 순간 다시 게이트가 된다.
- 공유 데모 계정을 만들지 않는다 : 데모용 시드 데이터는 사용자가 클릭 시에만 세션별로 주입한다.
  - RLS정책이 auth.uid()=user_id인데, 공유 데모계정을 만들려면 "단, 데모계정이면 누구나 조회가능"이라는 예외를 파야한다.
  - 시드는 가짜 데이터라 보안을 지킬 필요는 없다. 그러나 공유 계정으로만 얻을 수 있는 것이 하나도 없다.
  - RLS 예외 2개(조회, 수정)랑 주기적 리셋 배치가 필요한데, 세션별 주입은 INSERT함수 하나로 끝이고 익명세션이라 방문자 간 데이터 오염도 없다.
  - 체험목적이라 UPDATE까지 열어야하는데, 익명사용자에게 쓰기권한까지 주는 정책은 조건을 잘못 쓰면 실제 위험이 될 수 있다. 없어도 되는 예외는 만들지 않는다.
- 회원가입, 비밀번호 재설정, 이메일 인증 흐름을 만들지 않는다 : 승격 경로는 구글 OAuth 하나로 한정한다. 인증 UI 를 늘리는 것은 이 앱이 증명하려는 것과 무관하다.
