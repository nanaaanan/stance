# 002. 실거래를 자연키로 식별하고 금액까지 키에 넣은 이유

- 상태: 확정
  - 시점 : 코드 작성 전/선택 전
  - 질문 : 왜 A가 아니라, B인가 판단
  - 핵심 : 트레이드오프

## 맥락

거래 신고 기한이 30일이라 지난달 거래가 이번 달에도 계속 들어온다. 그래서 최근 3개월은 매달 다시 수집해야 한다. 실제로 며칠 사이에 매매는 148건에서 150건, 전월세는 1,130건에서 1,168건으로 늘었다.

문제는 **국토교통부 응답에 거래를 구분하는 ID 가 없다**는 것이다. 어떤 행이 "이미 받아둔 그 거래"인지 알 방법이 없으면, 다시 받을 때마다 같은 거래가 새 행으로 쌓인다. 3개월치를 서른 번 받으면 한 거래가 서른 행이 된다.

그래서 컬럼 몇 개를 묶어 거래를 구분하는 열쇠로 써야 한다. **어느 컬럼을 넣느냐가 이 결정의 전부다.** 강남구 36개월치 전부(매매 10,741행, 전월세 1,130행)로 후보를 확인했다.

## 검토한 선택지

### 1. 행 전체를 해시해서 열쇠로 쓴다

한 칸만 바뀌어도 다른 거래가 된다. 등기일은 계약 몇 달 뒤에 채워지는데, 그 순간 같은 거래가 새 행으로 들어온다.

### 2. 응답에 온 순서대로 번호를 매긴다

응답 순서가 조금이라도 달라지면 같은 거래가 다른 번호를 받는다. 전월세는 특히 위험하다. 확정일자 자료가 응답 앞부분에 몰려 오는 구조라 순서가 항상 같다고 볼 근거가 없다.

### 3. 금액을 뺀 열쇠 (단지, 계약일, 면적, 층)

금액은 정정될 수 있으니 빼자는 생각이다. 그러면 금액이 바뀌어도 같은 거래로 이어진다.

실측이 이걸 부정했다. 이 열쇠로 묶였는데 금액이 서로 다른 그룹이 21개 나왔고, **그 안에 정정된 것과 원래 다른 거래인 것이 섞여 있다.**

```
11680-4929 / 2024-06-23 / 59.92㎡ / 16층
   198,000 (동 120)
   214,500 (동 102)      <- 정정이 아니라 처음부터 다른 거래
```

동으로 가려낼 수도 없다. 동이 채워진 행이 78.9%뿐이다.

### 4. 금액을 넣은 열쇠 (단지, 계약일, 면적, 층, 금액)

### 5. 위에 동과 등기일까지 더한다

4번이 놓치는 별개 거래 6건을 살릴 수 있다. 하지만 **이 두 칸은 시간이 지나며 채워진다.**

| 컬럼 | 채워진 비율 | 언제 채워지나 |
| --- | --- | --- |
| 등기일 | 86.5% | 계약 몇 달 뒤 |
| 동 | 78.9% | 해제 행에서는 비어 있음 |

열쇠에 넣으면 **등기가 끝난 날 같은 거래가 새 행으로 다시 들어온다.** 1번과 같은 문제다. 게다가 같은 거래의 정상 행과 해제 행이 서로 다른 열쇠가 되어 하나로 합칠 수도 없다.

## 결정

**4번을 골랐다.**

```
trade  (apt_seq, deal_date, exclu_use_ar, floor, deal_amount)
rent   (apt_seq, deal_date, exclu_use_ar, floor, deposit, monthly_rent)
```

기준은 하나다. **거래가 살아 있는 동안 값이 변하지 않는 컬럼만 넣는다.**

강남구 36개월치 결과다.

| | 매매 | 전월세 |
| --- | --- | --- |
| 총 행 수 | 10,741 | 1,130 |
| 서로 다른 열쇠 | 10,183 | 1,094 |
| 열쇠가 겹쳐 합쳐지는 행 | 41 | 36 |
| **그중 진짜 다른 거래** | **6 (0.056%)** | **1 (0.088%)** |

## 감수한 것

열쇠가 같은 **진짜 별개 거래 6건(0.056%)이 1행으로 합쳐진다.**

```
럭키(963) / 2024-07-06 / 84.97㎡ / 6층 / 195,000
   101동
   102동      <- 두 건이 한 행이 된다
```

동을 열쇠에 넣으면 이 2건은 살릴 수 있다. 하지만 그 대가로 나머지 전부가 매달 새 행으로 쌓인다. **0.056%를 잃고 99.94%의 정확성을 지키는 쪽**을 골랐다. 건수 자체는 `trade_count` 컬럼에 남긴다.

금액을 열쇠에 넣었기 때문에 따라온 일이 하나 있다. **금액이 정정되면 같은 거래가 새 행으로 들어오고 옛 행이 남는다.** 그대로 두면 정정 전 금액이 최저가와 최고가를 흔든다. 그래서 옛 행을 지우지 않고 "응답에서 사라졌다"고 표시만 한다. 자세한 규칙은 `docs/data/schema.md` 에 있다.

## 포기한 것 - 무엇을 만들지 않기로 했고 왜

### 금액 정정을 이어 붙이는 로직

"이 행은 저 행의 정정이다"를 판단하는 규칙을 만들 수 없다. 금액이 다른 21개 그룹 안에 정정과 별개 거래가 섞여 있는데, **원본에 그 둘을 가를 정보가 없다.** 규칙을 만들면 그건 추측이고, 추측을 사실처럼 DB 에 넣는 셈이 된다.

대신 옛 행에 "사라졌다"는 표시만 남긴다. 무엇이 언제 사라졌는지는 알 수 있고, 어느 것이 어느 것의 정정인지는 모른다고 둔다.

### 해제된 거래를 골라내는 로직

열쇠가 같은 정상 거래가 2건 이상인데 해제 통지가 오면 어느 것이 해제됐는지 알 수 없다. 이것도 원본에 없는 정보다.

`ambiguous_cancel` 로 표시만 하고 통계에서는 둘 다 해제로 본다. **이 판단이 안전한 쪽인 것은 아니다.** 2건 중 1건만 해제됐는데 둘 다 빼면 실제보다 적은 거래로 계산하게 된다. 그런데도 이쪽을 고른 이유는 "해제됐을 수도 있는 거래를 시세에 넣지 않는다"이지 "틀려도 안전하다"가 아니다.

### 동시 실행을 막는 DB 제약

처음에는 수집 기록의 `running` 상태로 막으려 했다. 그런데 **기록과 잠금은 언제까지 남아 있어야 하는지가 정반대다.**

| 원하는 것 | 프로그램이 죽은 뒤 `running` 행이 |
| --- | --- |
| 기록: 여기서 죽었다는 증거 | 남아 있어야 함 |
| 잠금: 다음 시도가 들어올 수 있게 | 사라져야 함 |

같은 행이 둘 다 할 수 없다. 잠금으로 쓰면 전원이 나간 뒤 남은 행이 그 구간의 재시도를 영원히 막는다.

Postgres 의 advisory lock 도 쓸 수 없었다. 수집기가 PostgREST 를 거쳐 붙는데 **요청 하나가 곧 트랜잭션 하나**라 잠금이 응답과 동시에 풀린다.

**차단은 GitHub Actions 의 `concurrency` 설정이 맡는다.** 겹쳐 돌아도 데이터가 깨지지는 않는다. 같은 열쇠로 넣거나 고치는 방식이라 결과가 같다. 낭비되는 것은 API 호출 한도뿐이라, 차단은 실행을 관리하는 층에 두는 것이 맞다.

### 별개 거래 6건을 살리는 예외 규칙

"동이 다르면 별개로 본다" 같은 예외를 넣을 수 있다. 하지만 동이 78.9%만 채워져 있어서 **그 예외는 동이 있는 거래에만 적용된다.** 같은 상황인데 어떤 건 나뉘고 어떤 건 안 나뉘는 규칙이 된다.

## 남은 리스크

전용면적이 소수 5자리로 오면 `numeric(9,4)` 가 **에러 없이 조용히 반올림한다.** 그러면 서로 다른 두 면적이 같은 값이 되어 다른 거래가 한 행으로 합쳐질 수 있다.

강남구에는 5자리가 없었다. 25개 구로 넓힐 때 수집 스크립트가 원문 자릿수를 검사해야 한다.
