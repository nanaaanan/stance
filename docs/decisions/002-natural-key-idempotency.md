# 002. 매일 다시 받는 실거래를 자연키 upsert 와 변경 이력으로 저장한 이유

- 상태: 확정
  - 시점 : 코드 작성 전/선택 전
  - 질문 : 왜 A가 아니라, B인가 판단
  - 핵심 : 트레이드오프

## 맥락

거래 신고 기한이 30일이라 최근 1~2개월은 반드시 덜 들어와 있다. 정정과 해제도 나중에 반영된다. 그래서 **매일 최근 3개월을 다시 받아야 한다.** 실제로 며칠 사이에 매매는 148건에서 150건, 전월세는 1,130건에서 1,168건으로 늘었다.

그런데 **국토교통부 응답에는 거래를 구분하는 ID 가 없다.** 그래서 두 가지를 함께 정해야 한다.

1. **무엇을 보고 "같은 거래"라고 할 것인가**
2. **다시 받은 것을 어떻게 저장할 것인가**

1번이 안 정해지면 2번을 못 하고, 2번을 잘못 고르면 1번이 맞아도 데이터가 망가진다. 강남구 36개월치 전부(매매 10,741행, 전월세 1,130행)로 후보를 확인했다.

## 검토한 선택지 (1) 무엇을 보고 같은 거래라고 할 것인가

### 1-A. 행 전체를 해시한다

한 칸만 바뀌어도 다른 거래가 된다. 등기일은 계약 몇 달 뒤에 채워지는데, 그 순간 같은 거래가 새 행으로 들어온다.

### 1-B. 응답에 온 순서대로 번호를 매긴다

응답 순서가 조금이라도 달라지면 같은 거래가 다른 번호를 받는다. 전월세는 특히 위험하다. 확정일자 자료가 응답 앞부분에 몰려 오는 구조라 순서가 항상 같다고 볼 근거가 없다.

### 1-C. 금액을 뺀 자연키 (단지, 계약일, 면적, 층)

금액은 정정될 수 있으니 빼자는 생각이다. 그러면 금액이 바뀌어도 같은 거래로 이어진다.

실측이 이걸 부정했다. 이 조합으로 묶였는데 금액이 서로 다른 그룹이 21개 나왔고, **그 안에 정정된 것과 원래 다른 거래인 것이 섞여 있다.**

```
11680-4929 / 2024-06-23 / 59.92㎡ / 16층
   198,000 (동 120)
   214,500 (동 102)      <- 정정이 아니라 처음부터 다른 거래
```

동으로 가려낼 수도 없다. 동이 채워진 행이 78.9%뿐이다.

### 1-D. 금액을 넣은 자연키 (단지, 계약일, 면적, 층, 금액)

### 1-E. 위에 동과 등기일까지 더한다

1-D 가 놓치는 별개 거래 6건을 살릴 수 있다. 하지만 **이 두 칸은 시간이 지나며 채워진다.**

| 컬럼 | 채워진 비율 | 언제 채워지나 |
| --- | --- | --- |
| 등기일 | 86.5% | 계약 몇 달 뒤 |
| 동 | 78.9% | 해제 행에서는 비어 있음 |

자연키에 넣으면 **등기가 끝난 날 같은 거래가 새 행으로 다시 들어온다.** 1-A 와 같은 문제다. 게다가 같은 거래의 정상 행과 해제 행이 서로 다른 자연키가 되어 하나로 합칠 수도 없다.

## 검토한 선택지 (2) 다시 받은 것을 어떻게 저장할 것인가

| # | 안 | 정정 전 값이 남나 | 저장 용량 |
| --- | --- | --- | --- |
| 2-A | 자연키 upsert 만 한다 | **사라짐** | 최소 |
| 2-B | 받은 것을 전부 쌓고 최신 회차만 골라 쓴다 | 남음 | **너무 큼** |
| 2-C | **자연키 upsert + 값이 실제로 바뀐 행만 따로 기록** | 남음 | 최소 |

### 2-A. 자연키 upsert 만 한다

가장 단순하고 같은 거래는 항상 1행이 된다. 그런데 **정정 전 값이 그냥 사라진다.** 실거래를 다루면서 정정 이력을 못 남기는 것은 이 서비스가 하려는 일과 어긋난다.

### 2-B. 받은 것을 전부 쌓는다

수집 시각을 붙여 매일 전량을 넣고, 화면에서는 가장 최근 회차만 골라 쓰는 방식이다. 이력이 완전히 남는 대신 **DB 용량이 먼저 터진다.**

```
강남구 매매 실측          36개월 10,741건 -> 월평균 약 300건
25개 구 추정              월 6,000 ~ 9,000건
매일 최근 3개월 재수집     하루 2만 행 안팎
행당 250바이트, 90일 누적  약 450MB
Supabase 무료 플랜 한도    500MB
```

전월세는 여기 넣지도 않았다. 강남구 한 달만 1,168건이라 더하면 더 빨리 찬다. **파이프라인이 스스로 DB 를 채워 서비스를 멈추게 한다.**

## 결정

**1-D + 2-C 를 골랐다.**

```
자연키
  trade  (apt_seq, deal_date, exclu_use_ar, floor, deal_amount)
  rent   (apt_seq, deal_date, exclu_use_ar, floor, deposit, monthly_rent)

저장
  원장 테이블은 자연키 upsert 로 현재 상태 1행만 유지
  값이 실제로 바뀐 순간만 별도 이력 테이블에 기록
```

자연키에 넣을 컬럼을 고른 기준은 하나다. **거래가 살아 있는 동안 값이 변하지 않는 컬럼만 넣는다.**

강남구 36개월치 결과다.

| | 매매 | 전월세 |
| --- | --- | --- |
| 총 행 수 | 10,741 | 1,130 |
| 서로 다른 자연키 | 10,183 | 1,094 |
| 자연키가 겹쳐 합쳐지는 행 | 41 | 36 |
| **그중 진짜 다른 거래** | **6 (0.056%)** | **1 (0.088%)** |

2-B 가 사려던 것은 "정정과 해제 이력"이었다. 그런데 **하루에 넣는 2만 행 중 실제로 값이 바뀌는 행은 극히 적다.** 나머지는 어제와 글자 하나 다르지 않은 사본이다.

실측으로 확인했다. 같은 구간을 두 번째로 수집했더니 **변경 이력이 0건**이었다. 2-B 였다면 같은 상황에서 2만 행이 그대로 쌓였을 것이다.

바뀐 것만 남기면 같은 정보를 얻으면서, 덤으로 **"무엇이 언제 바뀌었나"를 매번 두 회차를 비교하지 않고 바로 읽을 수 있다.**

## 감수한 것

자연키가 같은 **진짜 별개 거래 6건(0.056%)이 1행으로 합쳐진다.**

```
럭키(963) / 2024-07-06 / 84.97㎡ / 6층 / 195,000
   101동
   102동      <- 두 건이 한 행이 된다
```

동을 자연키에 넣으면 이 2건은 살릴 수 있다. 하지만 그 대가로 나머지 전부가 매달 새 행으로 쌓인다. **0.056%를 잃고 99.94%의 정확성을 지키는 쪽**을 골랐다. 건수 자체는 `trade_count` 컬럼에 남긴다.

## 이력 기록을 애플리케이션이 아니라 DB 트리거에 둔 이유

수집 스크립트가 "값이 바뀌었으면 이력도 넣어라"를 직접 하게 할 수도 있었다. 그렇게 하지 않았다.

- SQL Editor 에서 손으로 고쳐도 기록이 남는다
- 나중에 다른 코드가 이 테이블을 고쳐도 마찬가지다
- **기록을 남기는 일을 부르는 쪽의 성실성에 맡기지 않는다**

비교할 때 `first_seen_at` 과 `last_seen_at` 두 칸은 뺀다. 이 둘은 다시 받을 때마다 무조건 바뀌므로, 넣으면 **"매일 전부 바뀌었다"가 되어 이력이 무의미해진다.**

## 이 방식이 못 잡는 것

**금액 정정은 이력에 안 남는다.**

자연키에 금액이 들어 있어서, 금액이 바뀌면 같은 거래가 **새 행으로 들어온다.** 트리거는 값을 고칠 때만 도는데 이 경우는 새로 넣는 것이라 걸리지 않는다. 옛 행은 지워지지도 않고 이력에도 안 남은 채 테이블에 남아 시세 계산에 계속 들어간다.

찾아내는 기준은 **"오늘 응답에 없었다"** 이다. 어떤 구간을 오늘 잘 받았는데 그 안의 어떤 행이 응답에 없었다면, 정정됐거나 취소된 것이다. 그런 행을 지우지 않고 `is_current = false` 로 표시한다. **이 표시가 다시 트리거를 타므로 정정 이력이 여기서 완성된다.**

시세와 판정 계산에는 항상 `where is_current` 를 붙인다.

> "이력이 남는다"고 말하려면 **어떤 변경이 안 남는지**를 함께 알고 있어야 한다. 트리거만 두고 정정 이력이 보존된다고 하면 사실과 다르다.

## 포기한 것 - 무엇을 만들지 않기로 했고 왜

### 금액 정정을 이어 붙이는 로직

"이 행은 저 행의 정정이다"를 판단하는 규칙을 만들 수 없다. 금액이 다른 21개 그룹 안에 정정과 별개 거래가 섞여 있는데, **원본에 그 둘을 가를 정보가 없다.** 규칙을 만들면 그건 추측이고, 추측을 사실처럼 DB 에 넣는 셈이 된다.

### 해제된 거래를 골라내는 로직

자연키가 같은 정상 거래가 2건 이상인데 해제 통지가 오면 어느 것이 해제됐는지 알 수 없다. 이것도 원본에 없는 정보다.

`ambiguous_cancel` 로 표시만 하고 통계에서는 둘 다 해제로 본다. **이 판단이 안전한 쪽인 것은 아니다.** 2건 중 1건만 해제됐는데 둘 다 빼면 실제보다 적은 거래로 계산하게 된다. 그런데도 이쪽을 고른 이유는 "해제됐을 수도 있는 거래를 시세에 넣지 않는다"이지 "틀려도 안전하다"가 아니다.

### 원본 응답을 그대로 보관하는 것

XML 원본은 강남구만 9MB 다. 25개 구면 230MB 쯤 된다. 레포에도 커밋하지 않기로 했고 DB 에도 두지 않는다.

**다시 확인할 수 있는 수단은 `docs/api/*.http` 가 담당한다.** 같은 요청을 다시 보낼 수 있으면 원본을 쌓아두는 것과 결과가 같다.

### 해제된 거래를 별도 테이블로 분리하는 것

같은 테이블에 `cdeal_type` 표시만 두기로 했다. 두 가지 이유다.

1. "정상 테이블에서 해제와 같은 자연키를 가진 행을 **지우는**" 동작은 매일 도는 파이프라인에서 **실행 순서에 따라 결과가 달라진다.** 다시 받을 때마다 결과가 같아야 한다는 전제가 깨진다
2. 상세 화면은 해제된 거래도 `해제됨` 표시와 함께 보여주기로 했다. 나눠 두면 화면마다 두 테이블을 다시 합쳐야 한다

**통계에서 빠지고 상세에 표시가 뜬다는 결과는 어느 쪽이든 같다. 달라지는 것은 "어떻게 빼는가" 뿐이다.**

### 동시 실행을 막는 DB 제약

처음에는 수집 기록의 `running` 상태로 막으려 했다. 그런데 **기록과 잠금은 언제까지 남아 있어야 하는지가 정반대다.**

| 원하는 것 | 프로그램이 죽은 뒤 `running` 행이 |
| --- | --- |
| 기록: 여기서 죽었다는 증거 | 남아 있어야 함 |
| 잠금: 다음 시도가 들어올 수 있게 | 사라져야 함 |

같은 행이 둘 다 할 수 없다. 잠금으로 쓰면 전원이 나간 뒤 남은 행이 그 구간의 재시도를 영원히 막는다.

Postgres 의 advisory lock 도 쓸 수 없었다. 수집기가 PostgREST 를 거쳐 붙는데 **요청 하나가 곧 트랜잭션 하나**라 잠금이 응답과 동시에 풀린다.

**차단은 GitHub Actions 의 `concurrency` 설정이 맡는다.** 겹쳐 돌아도 데이터가 깨지지는 않는다. 자연키 upsert 라 결과가 같다. 낭비되는 것은 API 호출 한도뿐이라, 차단은 실행을 관리하는 층에 두는 것이 맞다.

## 남은 리스크

전용면적이 소수 5자리로 오면 `numeric(9,4)` 가 **에러 없이 조용히 반올림한다.** 그러면 서로 다른 두 면적이 같은 값이 되어 다른 거래가 한 행으로 합쳐질 수 있다.

강남구에는 5자리가 없었다. 25개 구로 넓힐 때 수집 스크립트가 원문 자릿수를 검사해야 한다.
