# 트러블슈팅

이 프로젝트에서 실제로 예상치 못하게 막혔던 지점과 문제해결방법 기록

- 시점 : 코드 작성 후/선택 후
- 질문 : 왜 안됐고, 어떻게 고쳤나
- 핵심 : 원인 추적

---

## `permission denied for table _smoke` (42501, HTTP 403)

- **증상**: RLS 정책을 만들었는데도 insert/select 가 403
- **원인**: RLS 와 GRANT 는 별개의 층이다. RLS 는 "어느 행"을, GRANT 는 "이 테이블을 건드릴 수 있는가"를 정한다. GRANT 에서 막히면 RLS 는 평가되지도 않는다
- **해결**: `grant select, insert on table public.X to authenticated;`
- **재발 방지**: 새 테이블을 만들 때 GRANT 를 같은 SQL 블록에 넣는다. 공개 데이터는 anon+authenticated SELECT, 사용자 데이터는 authenticated 전체

## `relation "_smoke" already exists` (42P07)

- **증상**: 기존 SQL 아래에 GRANT를 붙여 재실행했더니 맨 위 create table에서 멈춤
- **원인**: SQL Editor 는 파일이 아니라 실행창이다. 편집창 전체를 위에서부터 다시 실행한다. 에러가 나면 그 뒤 문장은 실행되지 않는다
- **해결**: New query 로 빈 창을 열고 필요한 문장만 실행
- **재발 방지**: SQL은 중복되어도 무관하게 쓴다.(멱등성) 테이블 `create ... if not exists`, 정책 `drop policy if exists` 후 재생성, GRANT는 재실행 안전

## 로컬은 되는데 배포에서 세션이 안 잡힘

- **증상**: localhost 에서는 UUID 가 뜨는데 Vercel URL 에서는 "연결 중..." 에서 멈춤
- **원인**: Vercel 환경변수 미등록, 또는 등록했으나 재배포하지 않음
- **해결**: Settings &rarr; Environment Variables 에 Production/Preview/Development 3곳 모두 체크 &rarr; Deployments 에서 Redeploy
- **재발 방지**: 환경변수는 빌드 시점에 코드에 박힌다. 기존 배포에 소급 적용되지 않는다. 추가, 수정 후에는 항상 Redeploy

## `.env` 를 고쳤는데 반영되지 않음

- **증상**: 값을 바꿔도 이전 값으로 동작
- **원인**: Next.js 는 서버 시작 시점에 `.env` 를 읽는다
- **해결**: ⌃C 로 종료 후 `npm run dev` 재시작
- **재발 방지**: `.env` 를 만졌으면 무조건 재시작

## 같은 달을 다시 수집했더니 채워져 있던 값이 사라짐

- **증상**: 처음 수집 때 잘 들어갔던 등기일과 동이 두 번째 수집 후 비어 있다. 변경 이력에는 "값이 바뀌었다"는 기록만 쌓인다
- **원인**: Supabase 에 upsert 로 보내면 **보낸 값이 비어 있어도 그대로 덮어쓴다.** 원래 값을 남겨두는 처리가 없다. 비어 있는 칸만 빼고 보낼 수도 없다. 한 번에 보내는 행들의 칸 목록이 전부 같아야 하기 때문이다 (PGRST102)
- **해결**: 값을 고치기 직전에 끼어드는 트리거(BEFORE UPDATE)를 만들어, 새로 온 값이 비어 있으면 원래 값을 되돌려 놓는다. 이력을 남기는 트리거(AFTER UPDATE)보다 먼저 돌아서 가짜 기록도 안 생긴다
- **재발 방지**: upsert 로 채우는 테이블에 "한 번 채워지면 다시 비워질 일 없는 칸"이 있으면, 테이블을 만들 때 이 트리거도 같이 만든다. 에러가 안 나고 조용히 사라져서 나중에는 알아채기 어렵다

## 전월세 `preDeposit` 이 전부 비어 보임

- **증상**: `numOfRows=10` 으로 확인했더니 종전 보증금이 100% 공백 &rarr; "이 필드는 못 쓴다"고 잘못 판단함.
- **원인**: 응답이 정렬돼 있고 앞부분에 미분류 건이 몰려 있다. 강남·동작 모두 앞 10건의 `contractType` 공백률이 정확히 100%
- **해결**: `numOfRows=1000` 으로 전수 확인 &rarr; 갱신 계약의 99.3% 가 채워져 있었다
- **재발 방지**: 표본을 볼 때 표본이 어떻게 정렬되는지를 먼저 의심한다. 첫 페이지는 표본이 아니다

## main 에 push 했더니 `GH013 ... Required status check "semgrep" is expected.`

- **왜 켰나**: github actions의 workflow 검사 결과가 빨강이어도 Merge 버튼이 그대로 눌렸다. 표시등이 아니라 실제로 머지를 막는 관문으로 만들려고 default 브랜치 ruleset에 "검사 필수"를 켜봤다
- **증상**: 그 뒤로 파일 하나 고쳐서 `git push origin main` 한 것이 거부됨. 자동으로 도는 keepalive 커밋도 같은 이유로 막힌다
- **원인**: 타겟 브랜치에 '상태검사통과 조건(Require status checks to pass)'를 "필수"로 걸면, 검사에 통과했다는 기록이 없는 커밋은 아무도 못 올린다. 그런데 그 검사는 push 가 된 뒤에 도는 것이라 순서가 꼬인다. 사람이든 봇이든 똑같이 막힌다. 봇만 예외로 빼려고 봐도 개인 레포의 예외 목록에는 GitHub Actions가 없고, 넣을 수 있는 예외(admin, write)는 나 자신까지 통과시켜서 검사가 있으나 마나가 된다
- **해결**: Settings &rarr; Rulesets 에서 그 규칙을 `Disabled` 로 바꾼다. 지울 필요는 없다. 이미 들어간 커밋에는 영향이 없다
- **재발 방지**: **main에 직접 커밋하는 자동 작업이 있으면 "검사 필수 Rulesets"을 켜지 않는다.** 꼭 켜야 하면 그 자동 작업이 main이 아닌 다른 브랜치에 커밋하도록 먼저 바꾼다. 검사가 도는 것과 검사가 막는 것은 다른 일이고, 막게 만드는 순간 자동 작업이 먼저 죽는다

## 1,000 행씩 나눠 받았더니 같은 행이 중복되고 받을 때마다 결과가 다름

- **증상**: 한 구의 거래를 나눠 받았는데 같은 행이 40개 중복. 두 번 받으면 서로 다른 행 묶음이 온다. **그런데 총 행 수와 총 건수는 맞았다**
- **원인**: 나눠 받을 때 "몇 번째부터 몇 개" 방식을 쓴다. 이때 **정렬 기준이 여러 행에서 겹치는 값이면 순서가 매번 달라진다.** 그러면 앞 페이지에 왔던 행이 뒤 페이지에 또 오고, 어떤 행은 아예 안 온다. 정렬 기준으로 쓴 단지 번호는 한 단지에 거래가 여러 건이라 겹친다
- **해결**: 정렬 기준을 **겹치지 않는 칸**으로 바꾼다. `order=id`
- **재발 방지**: 나눠 받는 조회는 **정렬 기준이 유일한 값인지 먼저 확인한다.** 합계만 보면 못 잡는다. 빠진 만큼 중복이 채워 넣어서 총합이 맞아 보인다. 이번에도 총 행 수와 총 건수는 정상이었고, 파생 지표 하나가 1 어긋나서 겨우 드러났다
