# 실거래 원장 스키마

국토교통부 아파트 실거래 API 응답을 담는 4개 테이블.

|                     |                                                         |
| ------------------- | ------------------------------------------------------- |
| DDL                 | `supabase/migrations/20260818104853_deal_tables.sql`    |
| 설계 근거가 된 실측 | `data/recon-summary.md`                                 |
| API 호출 예시       | `docs/api/molit-trade.http`, `docs/api/molit-rent.http` |

<br/>

## 먼저 알아둘 용어 3개

| 용어   | 뜻                                                                                                                            |
| ------ | ----------------------------------------------------------------------------------------------------------------------------- |
| 자연키 | 원본 데이터에 이미 들어 있는 값들을 조합해 만든 식별자. 이 API 는 거래 ID 를 주지 않으므로 컬럼 조합으로 거래를 구분해야 한다 |
| upsert | "있으면 고치고 없으면 넣는다". 같은 자연키가 이미 있으면 UPDATE, 없으면 INSERT                                                |
| 멱등   | 같은 작업을 몇 번 해도 결과가 같은 성질. 같은 달 데이터를 다시 받아 넣어도 행 수가 늘지 않아야 한다                           |

<br/>

## 이 스키마가 푸는 문제

거래를 신고할 기한이 30일이라, 지난달 거래가 이번 달에도 계속 들어온다. 그래서 **최근 3개월은 매달 다시 수집한다.**

문제는 원본 응답에 **거래를 식별하는 ID 가 없다**는 것이다. 어떤 행이 "이미 받아둔 그 거래"인지 알 방법이 없으면, 다시 받을 때마다 같은 거래가 새 행으로 쌓인다.

그래서 컬럼 몇 개를 묶어 자연키로 쓴다. 강남구 36개월치 전량으로 그 조합이 거래를 유일하게 구분하는지 확인했다.

|                            | 매매       | 전월세     |
| -------------------------- | ---------- | ---------- |
| 총 행 수                   | 10,741     | 1,130      |
| 서로 다른 자연키 개수      | 10,183     | 1,094      |
| 자연키가 겹쳐 합쳐지는 행  | 41         | 36         |
| 그중 진짜 다른 거래였던 것 | 6 (0.056%) | 1 (0.088%) |

<br/>

## 테이블 4개와 관계

```
                  수집 배치 (Python)
                         |
         +---------------+------------------+
         v                                  v
    +---------+                        +---------+
    |  trade  |  <-- aptSeq 로 조인 -->  |  rent   |
    |  매매    |                        |  전월세   |
    +---------+                        +---------+
         |                                  |
         +----- 값이 바뀌면 트리거 발동 ----------+
                         |
                         v
                +-----------------+
                | deal_change_log |   정정, 해제 이력만 기록
                +-----------------+
                         ^
                      run_id
                         |
                +-----------------+
                |   collect_run   |   수집 작업 자체를 기록
                +-----------------+
```

| 테이블            | 한 행이 뜻하는 것               | 다시 수집하면              |
| ----------------- | ------------------------------- | -------------------------- |
| `trade`           | 매매 거래 1건의 **현재 상태**   | 같은 거래는 그 행을 고침   |
| `rent`            | 전월세 계약 1건의 **현재 상태** | 같은 계약은 그 행을 고침   |
| `deal_change_log` | 값이 바뀐 순간 1회              | 안 바뀌면 아무것도 안 쌓임 |
| `collect_run`     | 수집 시도 1회                   | 덮어쓰지 않고 계속 쌓임    |

### 매매와 전월세를 한 테이블로 합치지 않은 이유

응답 필드가 서로 다르다.

- 전월세에는 해제(`cdealType`), 직거래(`dealingGbn`) 필드가 **아예 없다**
- 전월세에는 법정동 코드(`umdCd`)가 없다
- 전월세 도로명은 `"삼성로 212"`처럼 **번지가 이미 붙어서 온다.** 매매식으로 도로명 + 번지를 조립하면 `"삼성로 212 212"` 가 된다

합치면 절반이 빈 칸인 컬럼이 생기고, 무엇보다 서로 다른 파싱 규칙이 한 코드에 섞인다.

### 두 테이블을 잇는 키는 `aptSeq`

같은 단지의 매매와 전월세를 연결할 때는 `apt_seq` 를 쓴다. 양쪽 응답 모두 이 값을 주고, 강남구 실측에서 빠진 행이 0건이었다.

단지 관리정보(세대수, 좌표 등)는 서울시 공동주택 CSV 에 있는데, 그쪽은 `aptSeq` 가 없어서 **도로명 주소로만** 붙인다. 단지명이나 지번으로 붙이면 엉뚱한 단지에 잘못 매칭된다. 관련 테이블은 아직 만들지 않았다.

<br/>

## 자연키

```
trade  (apt_seq, deal_date, exclu_use_ar, floor, deal_amount)
rent   (apt_seq, deal_date, exclu_use_ar, floor, deposit, monthly_rent)
```

### 넣지 않은 컬럼과 이유

핵심 기준은 **"거래가 살아있는 동안 값이 변하지 않는가"** 다.

| 컬럼                              | 왜 뺐나                                         | 실제로 채워진 비율 |
| --------------------------------- | ----------------------------------------------- | ------------------ |
| `rgst_date` (등기일)              | 계약하고 몇 달 뒤에 채워진다                    | 86.5%              |
| `apt_dong` (동)                   | 해제 행에서는 비어 있고, 시간이 지나며 채워진다 | 78.9%              |
| `cdeal_type` / `cdeal_day` (해제) | 해제될 때 새로 생긴다                           | 6.5%               |

이런 칸을 키에 넣으면 두 가지가 동시에 망가진다.

1. 같은 거래인데 정상 행과 해제 행의 키가 달라져서 하나로 못 합친다
2. **등기가 완료된 날, 이미 있던 거래가 새 행으로 또 들어온다.** 매달 다시 수집하는 구조에서 이건 치명적이다

### 대신 감수한 것 - 트레이드오프

자연키가 같은 진짜 별개 거래 6건(0.056%)이 1행으로 합쳐진다. 예를 들어 `럭키(963)` 아파트에서 2024-07-06 에 84.97제곱미터 6층이 195,000만원에 두 건 거래됐는데, 하나는 101동 하나는 102동이다.

`apt_dong` 을 키에 넣으면 이 2건은 살릴 수 있지만, 위 2번 때문에 전체가 무너진다. **0.056% 를 잃고 멱등성을 지키는 쪽**을 택했다.

#### `trade_count` 계산 규칙

자연키가 같은 행이 2개 오면 DB 에는 1행만 남는다. 그런데 그게 진짜 2건의 거래일 수도 있다. 그래서 건수를 따로 센다.

```
거래 건수를 셀 때는 count(*) 가 아니라 sum(trade_count) 를 쓴다
```

원본에 거래 ID 가 없어서 확정할 수 없고, 아래 규칙으로 **추정**한다.

| 같은 자연키로 묶인 원본 행  | `trade_count` | `cdeal_type` | `ambiguous_cancel` | 의미                                  |
| --------------------------- | ------------- | ------------ | ------------------ | ------------------------------------- |
| 정상 1건                    | 1             | NULL         | false              | 보통의 거래                           |
| 정상 n건 (n >= 2)           | n             | NULL         | false              | 같은 날 같은 층 같은 금액의 별개 거래 |
| 정상 0 + 해제 1건           | 1             | `O`          | false              | 해제 통지만 도착                      |
| 정상 0 + 해제 n건           | 1             | `O`          | false              | 같은 해제가 중복 통지됨               |
| 정상 1 + 해제 있음          | 1             | `O`          | false              | 그 거래가 해제됨                      |
| 정상 n (n >= 2) + 해제 있음 | n             | `O`          | **true**           | 어느 거래가 해제됐는지 모름           |

두 가지를 함께 봐야 한다.

- **해제 행은 거래가 아니라 상태 통지라서 세지 않는다.** 다만 해제 통지가 왔다는 것은 해제할 거래가 있었다는 뜻이므로, 정상 행이 하나도 없어도 거래는 1건으로 본다
- **병합 결과는 "해제 행"이 아니라 "정상 행에 해제 도장을 찍은 것"이다.** 해제 행에는 동과 등기일이 비어 있어서, 그쪽만 남기면 단지 상세 화면에 거래를 보여줄 수 없다

#### `is_current` 마킹 규칙

금액이 자연키에 들어 있어서 **신고 금액이 정정되면 같은 거래가 새 행으로 들어오고, 옛 행은 그대로 남는다.** 변경 이력 트리거는 UPDATE 만 잡으므로 이 경우를 못 본다. 그냥 두면 정정 전 금액이 최저가와 최고가를 흔든다.

| 항목            | 내용                                                                       |
| --------------- | -------------------------------------------------------------------------- |
| 언제 표시하나   | 어떤 (구, 계약월) 을 성공적으로 수집한 직후                                |
| 무엇을 표시하나 | 그 (구, 계약월) 에 속하면서 `last_seen_at` 이 이번 수집 시각보다 이전인 행 |
| 어떻게 하나     | 지우지 않고 `is_current = false` 로만 표시                                 |
| 되돌리기        | 다음 회차 응답에 다시 나타나면 upsert 가 `true` 로 되돌린다                |

**삭제가 아니라 표시인 이유**는 이 UPDATE 가 트리거를 타기 때문이다. "무엇이 언제 사라졌는지"가 `deal_change_log` 에 자동으로 쌓인다. 지워버리면 정정 이력 보존이라는 목표 자체가 성립하지 않는다.

```
시세, 판정 계산에는 항상 where is_current 를 붙인다. 예외 없다
```

한계가 하나 있다. 최근 3개월만 다시 수집하므로 **그보다 오래된 구간에서 일어난 정정과 해제는 반영되지 않는다.**

**인덱스 3개**

| 이름                 | 컬럼                        | 용도                                        |
| -------------------- | --------------------------- | ------------------------------------------- |
| `trade_natural_key`  | 자연키 5칸                  | unique. upsert 가 "같은 행"을 판단하는 기준 |
| `trade_sgg_ym_idx`   | `(sgg_cd, deal_ym)`         | 구/월 단위 집계                             |
| `trade_apt_date_idx` | `(apt_seq, deal_date desc)` | 단지 상세 화면                              |

검색 화면 쿼리가 정해지기 전에는 인덱스를 늘리지 않는다. 인덱스는 조회를 빠르게 하는 대신 쓰기를 느리게 하므로, 쓸지 안 쓸지 모르는 인덱스는 비용만 낸다.

### collect_run

**수집 작업 일지다.** 실거래 데이터가 아니라 "어느 구의 어느 달을 언제 어떻게 수집했나"를 적는다.

| 질문            | 컬럼                                                                                      |
| --------------- | ----------------------------------------------------------------------------------------- |
| 무엇을 수집했나 | `kind` (`trade`/`rent`), `lawd_cd`, `deal_ym`                                             |
| 어떻게 끝났나   | `status` (`running`/`ok`/`error`), `started_at`, `finished_at`, `error_code`, `error_msg` |
| 얼마나 받았나   | `total_count`, `fetched_rows`, `page_count`                                               |
| 무엇이 바뀌었나 | `inserted_count`, `updated_count`, `unchanged_count`                                      |

**왜 필요한가**

- **이어하기.** 25구 x 36개월 = 900번 호출인데, 중간에 끊기면 어디까지 했는지 알아야 한다. 배치는 GitHub Actions 에서 도는데 매번 새 컴퓨터가 만들어지므로 파일로 남길 수 없다
- **멱등성 확인.** 같은 구간을 두 번째 수집하면 `inserted 0 / updated 0` 이 나와야 정상이다. 이 숫자가 없으면 "안 늘어났다"를 확인할 방법이 없다
- **신고 유입 관측.** 같은 달인데 회차마다 `total_count` 가 늘어난다. 덮어쓰면 이 변화가 사라져서 "최근 몇 개월을 다시 받아야 하나"를 판단할 재료가 없어진다

**`running` 은 기록이지 잠금이 아니다.** 처음엔 "같은 구간에 `running` 이 하나만 있게 하면 중복 실행이 막히겠다"고 생각했는데, 이게 모순이다.

| 원하는 것                        | 크래시 후 `running` 행이 |
| -------------------------------- | ------------------------ |
| 기록: 여기서 죽었다는 증거       | 남아 있어야 함           |
| 잠금: 다음 시도가 들어올 수 있게 | 사라져야 함              |

잠금으로 쓰면 전원이 나간 뒤 남은 `running` 행이 그 구간의 재시도를 **영원히 막는다.** `try/finally` 로도 못 막는다.

**중복 실행 차단은 DB 가 아니라 GitHub Actions 가 맡는다.**

```yaml
concurrency:
  group: collect-${{ github.workflow }}
  cancel-in-progress: false
```

처음에는 Postgres 의 advisory lock 을 쓰려 했는데 이 구조에서는 쓸 수 없다.

- 수집기는 PostgREST 를 거쳐 DB 에 붙는다. **요청 하나가 곧 트랜잭션 하나**라 잠금이 응답과 동시에 풀린다. 수집 전체 구간을 덮지 못한다
- 세션 단위 잠금도 안 된다. PostgREST 는 접속을 돌려쓰기 때문에 어느 접속에 잠금이 걸릴지 모르고, 푸는 것도 보장되지 않는다

겹쳐 돌아도 데이터가 깨지지는 않는다. 자연키 upsert 라 결과가 같기 때문이다. 낭비되는 것은 API 호출 한도뿐이다. 그래서 차단은 실행을 관리하는 층에 두는 것이 맞다.

### deal_change_log

값이 실제로 바뀐 순간만 기록한다. `trade` 나 `rent` 가 UPDATE 될 때 트리거가 자동으로 넣는다.

| 컬럼                 | 비고                                         |
| -------------------- | -------------------------------------------- |
| `source_table`       | `trade` / `rent`                             |
| `trade_id` `rent_id` | 둘 중 정확히 하나만 채워진다 (CHECK 로 강제) |
| `run_id`             | 어느 수집 회차에서 바뀌었나                  |
| `changed_fields`     | 바뀐 컬럼 이름들. 이름순으로 고정            |
| `old_row`            | 바뀌기 전 행 전체                            |

**트리거 동작**

| 항목          | 내용                                                                          |
| ------------- | ----------------------------------------------------------------------------- |
| 시점          | UPDATE 이후에만. INSERT 는 기록 안 함 (최초 등장은 `first_seen_at` 이 답한다) |
| 비교 방식     | 바뀌기 전과 후를 컬럼별로 비교                                                |
| 비교에서 제외 | `first_seen_at`, `last_seen_at`                                               |
| 안 바뀌었으면 | 아무것도 안 넣는다                                                            |

**여기에 쌓이는 것과 안 쌓이는 것**

| 구분          | 무엇이 바뀔 때                            |
| ------------- | ----------------------------------------- |
| 쌓인다        | 해제 통지가 도착 (`cdeal_type` 이 채워짐) |
| 쌓인다        | 등기일, 동이 뒤늦게 채워짐                |
| 쌓인다        | 계약구분, 종전보증금이 뒤늦게 채워짐      |
| 쌓인다        | `is_current` 가 false 로 바뀜             |
| **안 쌓인다** | **금액 정정**                             |

금액이 자연키에 들어 있어서, 금액이 바뀌면 **다른 거래로 인식되어 새 행이 생긴다.** 그래서 변경 이력에 안 잡힌다.

금액을 자연키에서 빼는 방법도 검토했지만 실측이 부정했다. 금액만 다른 21개 그룹 안에 "정정된 것"과 "원래 다른 거래인 것"이 섞여 있고, 원본만으로는 구분할 수 없다. 예를 들어 `11680-4929` 의 2024-06-23 59.92제곱미터 16층은 198,000(120동)과 214,500(102동)으로 처음부터 다른 거래다.

대신 응답에서 사라진 옛 행을 지우지 않고 `is_current = false` 로 표시한다. 이 UPDATE 가 트리거를 타므로 **"이 거래가 응답에서 빠졌다"는 사실은 이력에 남는다.**

**원본을 지워도 이력은 안 지워진다.** FK 를 `on delete restrict` 로 걸었고, 수집 스크립트 계정에서 DELETE 권한 자체를 뺐다. "구간을 지우고 새로 넣자"는 흔한 로더 구현 한 줄이 정정 이력까지 날리는 걸 막기 위해서다. 원본 API 는 과거 상태를 돌려주지 않으므로 한 번 지우면 복구할 수 없다.

## 수집 스크립트가 지켜야 할 규칙

DDL 로는 강제할 수 없다. 어기면 멱등성이 깨진다.

### 1. 빈 문자열은 NULL 로 바꿔서 보낸다

빈 값과 "값이 없다"를 DB 에서 구분하기 위해서다. 실측에서 "한쪽은 비어 있고 한쪽은 채워진" 중복이 가장 많았다 (매매 19건, 전월세 11건).

**빈 값이 이미 채워진 값을 덮지 않게 막는 것은 스크립트가 아니라 DB 트리거다.**

수집기는 PostgREST 로 upsert 를 보내는데, PostgREST 가 만드는 SQL 은 이 모양이다.

```sql
ON CONFLICT (자연키) DO UPDATE SET apt_dong = EXCLUDED.apt_dong
```

`coalesce` 가 없다. **payload 의 NULL 이 기존 값을 그대로 지운다.** payload 에서 NULL 인 키를 빼는 방법도 못 쓴다. PostgREST 는 한 번에 보내는 객체들의 키가 전부 같기를 요구하고(`PGRST102`), 값 조합별로 요청을 쪼개면 묶어 보내는 의미가 없어진다.

그래서 `trade` 와 `rent` 에 BEFORE UPDATE 트리거를 걸어 NULL 을 옛 값으로 되살린다.

```
trg_trade_keep_filled   supabase/migrations/20260820160000_keep_filled_values.sql
trg_rent_keep_filled
```

이력 트리거(AFTER UPDATE)보다 먼저 돌기 때문에 가짜 변경 이력도 생기지 않는다.

### 2. 배치 안에서 자연키별로 먼저 합친 뒤 한 번에 넣는다

전월세는 확정일자 자료와 거래신고 자료가 **같은 응답에 함께 온다.** 행을 하나씩 순서대로 넣으면 **어느 것이 먼저 오느냐에 따라 결과가 달라진다.** 순서가 바뀌면 결과가 바뀌므로 멱등하지 않다. 1번 규칙만으로는 못 막는다.

합치는 단계가 **두 개**라는 점에 주의한다. 규칙이 서로 다르다.

| 단계 | 무엇과 무엇을 합치나                  | 규칙                            |
| ---- | ------------------------------------- | ------------------------------- |
| 1    | 같은 응답 안의 여러 행 -> 넣을 값 1개 | 아래 표                         |
| 2    | 넣을 값 1개 -> DB 에 이미 있는 행     | `coalesce(excluded.x, trade.x)` |

**1단계: 응답 안에서 합치기**

| 필드                                       | 규칙                                                                        | 왜                                                                     |
| ------------------------------------------ | --------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 자연키 5칸                                 | 그룹 안에서 항상 같다                                                       | 같은 키로 묶였으니 정의상 동일                                         |
| `cdeal_type`                               | `O` 우선                                                                    | 하나라도 해제면 그 거래는 해제된 것                                    |
| `cdeal_day`                                | 가장 이른 날                                                                | 해제는 한 번 일어난다. 첫 통지가 실제 시점에 가깝다                    |
| `apt_dong`, `rgst_date`, 그 밖의 부가 필드 | 비어 있지 않은 값 우선. **서로 다른 값이 둘 이상이면 채우지 않는다 (NULL)** | 어느 값이 맞는지 모른다. 하나를 고르면 틀릴 수 있는 사실을 넣는 것이다 |

마지막 줄이 이 프로젝트의 원칙과 직결된다. **모르는 것은 추측으로 메우지 않고 비워 둔다.**

**2단계: DB 와 합치기**

여기서는 NULL 이 기존 값을 덮지 않는다. **1번 규칙의 BEFORE UPDATE 트리거가 막는다.** 1단계에서 값이 충돌해 NULL 이 됐더라도, DB 에 이전 회차가 확보해 둔 값이 있으면 그쪽이 남는다.

### 3. 빈 값 처리를 감사 스크립트와 똑같이 한다

기준은 `scripts/recon.py` 의 `_BLANK_DEFAULT` 다.

- `monthly_rent` 만 빈 값 -> `0`
- 나머지 자연키 칸은 빈 값이면 그 행을 버린다
- `deposit` 은 기본값을 두지 않는다. **"안 적혀 있다"와 "0원이다"는 다른 사실이다**

적재가 감사보다 느슨하면 DB 행이 더 많아지고, 엄격하면 더 적어져서 앞서 확인한 유일성 결과를 그대로 쓸 수 없다.

### 4. (수집종류, 구, 계약월) 한 칸 = 트랜잭션 한 개

중간에 에러가 나면 그 칸을 통째로 되돌리고 `status = 'error'` 로 남긴다. 반쯤 들어간 상태를 만들지 않는다.

### 5. 수집 회차 번호를 요청에 실어 보낸다

이력 트리거가 이 값을 읽어 `deal_change_log.run_id` 를 채운다. 빠뜨리면 "이 정정이 어느 회차에서 발견됐나"를 알 수 없다.

번호를 넘기는 방법이 두 가지고, 누가 고치느냐에 따라 다르다.

| 누가 고치나 | 방법 |
| --- | --- |
| 수집 스크립트 (PostgREST) | 요청 헤더 `X-Run-Id: <collect_run.id>` |
| SQL Editor 에서 직접 | `select set_config('stance.run_id', '<collect_run.id>', true);` |

스크립트가 `set_config` 를 못 쓰는 이유는 **PostgREST 가 요청마다 새 세션이라 심어둔 값이 남지 않기** 때문이다. 대신 PostgREST 는 요청 헤더를 그 트랜잭션 안에서 읽게 해준다.

`upsert` 와 `is_current` 마킹 **양쪽 모두** 헤더를 붙여야 한다. 한쪽만 붙이면 그쪽 이력에만 번호가 남는다.

### 6. 전용면적 계산에 실수(float) 를 거치지 않는다

`Decimal` 로 소수 4자리 반올림한다 (`recon.py` 의 `_norm_one` 과 동일). float 는 근사값이라 `84.98` 이 `84.98000000000001` 로 저장될 수 있고, 그러면 자연키가 흔들려 같은 거래를 다른 거래로 본다.

`numeric(9,4)` 는 소수 5자리가 들어와도 **에러 없이 조용히 반올림한다.** 실측상 5자리는 없었지만, 25개 구로 넓힐 때 스크립트가 원문 자릿수를 검사해야 한다.

### 7. 날짜 변환에 실패하면 추측으로 메우지 않는다

없는 날짜면 그 행을 버리고 개수를 기록한다.

## 정제 규칙이 어디서 도는가

같은 "정제"라도 도는 자리가 다르다. 새 규칙을 넣을 때 어느 쪽인지 먼저 정한다.

| 규칙                                    | 위치                             | 언제               |
| --------------------------------------- | -------------------------------- | ------------------ |
| 자연키 중복 병합 (해제 쌍 합치기)       | `scripts/collect.py`             | 적재 직전          |
| 빈 값이 채워진 값을 덮지 않게           | DB 트리거 `keep_filled_values`   | UPDATE 직전        |
| 직거래 제외, 해제 제외 후 최저가/최고가 | `src/lib/domain/clean.ts` (예정) | 화면에서 판정할 때 |

기준은 **"원본을 바꾸는가"** 다.

- 병합은 저장 형태를 정하는 일이라 적재 때 한 번만 돈다
- 직거래와 해제 제외는 원본을 지우지 않고 **볼 때 걸러내는** 일이라 판정 시점에 돈다. 그래서 DB 에는 직거래도 해제도 그대로 남아 있다

## 권한

`GRANT` 와 RLS 는 서로 다른 층이다. `GRANT` 에서 막히면 RLS 는 검사조차 되지 않는다 (에러 42501).

| 테이블                          | 브라우저 (anon / authenticated) | 수집 스크립트 (service_role) |
| ------------------------------- | ------------------------------- | ---------------------------- |
| `trade` `rent`                  | 읽기만                          | 읽기, 넣기, 고치기           |
| `deal_change_log` `collect_run` | 접근 불가                       | 읽기, 넣기, 고치기           |

- RLS 는 4개 테이블 모두 켠다. `trade`/`rent` 에만 전체 읽기 정책을 둔다
- `anon` 을 넣는 이유: 익명 세션 발급이 끝나기 전에 데이터를 요청하는 구간이 있고, 그때 역할은 `authenticated` 가 아니라 `anon` 이다
- 수집 스크립트에 **DELETE 를 주지 않는다.** 이 설계는 upsert 와 표시만 쓰므로 지울 일이 없다. 권한이 없으면 실수도 없다
- Supabase 는 새 테이블에 권한을 자동으로 주므로 `revoke` 를 먼저 하고 `grant` 한다. `grant` 는 더하기만 하기 때문이다

on conflict (apt_seq, deal_date, exclu_use_ar, floor, deal_amount) do update

### 값을 일부러 비우려면 트리거를 잠깐 꺼야 한다

`keep_filled_values` 트리거는 보호 목록에 있는 칸을 NULL 로 바꾸는 것을 막는다. 빈 값이 실수로 기존 값을 덮는 것을 막으려고 만든 것이라, 의도적인 삭제도 같이 막힌다.

```sql
alter table public.trade disable trigger trg_trade_keep_filled;
-- 원하는 UPDATE
alter table public.trade enable  trigger trg_trade_keep_filled;
```

### 넣은 수와 고친 수는 앞뒤를 재서 구한 값이다

PostgREST 는 upsert 를 하고 나서 넣은 건지 고친 건지 알려주지 않는다. 그래서 적재 전후로 행 수를 세고, 그 사이에 늘어난 이력 행 수를 고친 수로 본다.

기준을 시각이 아니라 **이력 테이블의 `id`** 로 잡았다. 시각으로 자르면 스크립트가 도는 컴퓨터 시계와 DB 시계가 어긋날 때 틀리기 때문이다.

**같은 구간을 두 프로세스가 동시에 돌면 이 계산이 어긋난다.** 데이터가 깨지지는 않지만(자연키 upsert 라 결과는 같다) 기록된 숫자를 믿을 수 없게 된다. 동시 실행을 막는 것은 GitHub Actions 의 `concurrency` 설정이다.

### 해제된 거래를 특정할 수 없을 때

자연키가 같은 정상 거래가 2건 이상인데 해제 통지가 있으면, **어느 거래가 해제됐는지 알 수 없다.** 원본에 1:1 로 대응하는 거래 ID 가 없어서 생기는 정보 부족이라 알고리즘으로 풀리지 않는다.

이 경우 `ambiguous_cancel = true` 로 표시하고, 통계에서는 **해제 우선**으로 판정한다.

**이 판정이 "안전한 쪽"인 것은 아니다.** 정상 2건 중 1건만 해제됐는데 2건 모두 해제로 취급하면 유효 표본을 실제보다 적게 잡는 것이다. 그런데도 이쪽을 고른 이유는 **없는 정보를 만들지 않는다**는 원칙 때문이다. "해제됐을 수도 있는 거래를 시세에 넣지 않는다"이지 "틀려도 안전하다"가 아니다.

DB 에 표시를 남기는 비용은 컬럼 하나뿐이고, 대신 나중에 "왜 이 거래가 통계에서 빠졌지"를 추적할 수 있다. 빈도는 `data/recon-summary.md` 에 실측으로 기록한다.

### 단지 정보가 두 곳에 있을 때 어느 쪽이 진실인가

`trade` 에는 단지 속성(`apt_nm`, `road_nm`, `jibun`, `build_year`, `umd_nm`)이 **거래 행마다 반복해서** 들어 있다. 나중에 단지 마스터 테이블이 생기면 같은 사실이 두 곳에 존재하게 된다.

| 어디                 | 무엇인가                       | 화면이 읽나 |
| -------------------- | ------------------------------ | ----------- |
| `trade` 의 단지 속성 | 그 시점 응답의 **원본 스냅샷** | 아니오      |
| 단지 마스터 (예정)   | 화면이 읽는 **유일한 곳**      | 예          |

중복이지만 `trade` 쪽을 지우지 않는다. 매일 다시 수집하면 **마스터에 없는 `apt_seq` 가 들어오는데**, 그때 그 단지 정보의 유일한 출처가 거래 행이기 때문이다. 새 단지를 찾는 것도 `수집된 apt_seq 집합 - 마스터의 apt_seq 집합` 한 줄이면 끝난다.

단지 마스터의 상세 설계는 그 테이블을 만들 때 정한다.
